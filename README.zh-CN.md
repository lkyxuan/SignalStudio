# SignalStudio

[English](README.md) | **中文版**

一个以本地数据为主的设计工作台，用于梳理数据产品背后的定义、公式、设计理由、注意事项和依赖关系。

## 运行

### Mac 独立 App

在已安装项目依赖的 Mac 上运行 `npm run desktop:build`（需要 Xcode Command Line Tools），生成 `~/Applications/SignalStudio.app`。双击 App 即可打开独立工作台窗口，也可拖入 Dock。构建后日常使用不需要启动 Vite 或运行 Node。

App 从构建时的项目路径加载 `dist/`，使用构建时的 Python 和该项目的 `data/logic.db`。它在 `127.0.0.1:18787` 启动服务；仅复用健康检查确认属于同一项目且前端已构建的服务。重复打开回到已有窗口；关闭最后一个窗口或按 Command-Q 退出，停止它自行启动的服务，保留复用的服务。启动错误显示在窗口中，后台日志在 `~/Library/Logs/SignalStudio/server.log`。

这是本机应用外壳，尚未包含 Python 或项目文件，也未做分发公证。移动项目、删除 Python 或更新前端源码后，应重新构建；复制 App 到其他电脑不能独立运行。验证时检查首次启动、重复打开、退出重开，以及已有同项目服务和其他程序占用 18787 时的行为。设计依据与审批：[Notion 任务](https://app.notion.com/p/3f4038a63d5a8182b1e8e094efee2e51)。

### 开发服务

需要 Node.js 22+ 和 Python 3.9+。

```bash
npm install
npm run dev
```

打开 [http://127.0.0.1:5173](http://127.0.0.1:5173)。API 在 8787 端口运行。SQLite 数据库保存在 `data/logic.db`；可通过 `SIGNALSTUDIO_DB` 指定其他路径。启动时会移除未使用的 V2 记录类型节点，并以应用自身维护的上游操作作为来源基线。一次性迁移会补齐这些节点退役后留下的编号间隙；此后的删除操作不会复用引用编号。

如果要在另一台电脑上使用同一份项目数据，请先停止本地服务，再通过 GitHub Desktop 提交或拉取 `data/logic.db` 的变更。同步后重新启动服务。该数据库包含在这个公开仓库中。

实际回填快照 `data/table-1006-backfill.json` 也通过 Git 同步。取样 Agent 导入或直接校验写入后，提交并推送该文件；另一台电脑拉取仓库、重新打开 #1006 面板即可读取，无需再次导入。页面保存不会自动提交 Git。

Vite 也会监听网络接口。若要从同一 Tailscale 网络中的其他设备访问开发站点，在本机运行 `tailscale ip -4`，然后在另一台设备打开 `http://<本机-IP>:5173`。API 仍在本地运行，由 Vite 的 `/api` 代理转发请求。

如果要以单服务方式运行构建产物：

```bash
npm run build
npm run preview
```

然后打开 [http://127.0.0.1:8787](http://127.0.0.1:8787)。

## MVP 已包含的功能

- 十八种可见的设计节点类型，以及有方向的依赖连线。节点库区分数据来源、处理步骤、业务表和输出。`assets`、`asset_identifiers`、`asset_relationships` 和 `asset_monitoring_rules` 是固定且可连接的表引用，采用独立的外观。它们表示规划中的访问目标，目前没有连接真实业务表或记录。总览会在同一张图中显示所有来源与表，包括尚未连接的引用；信号路径和资产知识路径是对同一张图的不同筛选。系统不会自动创建处理步骤或表访问连线。
- 围绕信号进行规划：创建信号节点，描述各项输入数据需求和期望样例，再匹配已有的爬虫字段。未匹配的需求会保留在图中，并可复制为提供给爬虫组的需求清单。匹配字段时会创建来源节点、连接和字段使用关系，同时保留原始需求。
- 每个信号节点都有设计指引，将决策问题、观察窗口、计算方法、触发规则、输出契约、验证计划和已记录的观察放在一起。检查清单统计已填写的设计要素；在评估真实数据之前，它不会声称信号有效。
- 以 `catalog/source-contracts.v1.json` 为依据的各操作字段目录。该契约定义了 8 个上游来源、36 个操作、2 个 Kaito MCP 参考资源，以及当前从官方资料和保存的 API/MCP 响应中选取的 265 个字段条目。每个操作和参考资源都有独立的来源节点。样本中的字段路径只是已知范围的下限或规划中的选择，不代表完整输出，也不代表爬虫已经实际产出这些字段。
- **字段用途与案例**视图与字段选择器、来源节点详情读取同一份应用上游契约，展示字段原始路径、用途、证据类别和标注来源的示例值。产品已不再加载旧版 V2 记录类型目录。
- [来源字段审计](docs/SOURCE_FIELD_AUDIT.md)逐一核对八个上游的文档和固定版本爬虫代码。[来源输入审计](docs/SOURCE_INPUT_AUDIT.md)列出各上游操作的必填与可选调用参数，并明确标注未知契约。[Few Understand 集成契约](docs/FEWUNDERSTAND_INTEGRATION.md)规定爬虫项目如何使用应用上游契约，并回报实施证据。每个来源节点都会展示输入与输出的依据。保存的 DEX Screener 响应将一个 `pairs[0]` 对象展开为独立卡片；它是上游响应样本，不是爬虫消息的证据。
- 用户创建的输出字段可以指定单位、数值范围，以及计算或归一化规则。目录中的示例只来自明确标注的 API 响应、上游测试样本或已审阅的 V2 示意数据；应用不会在运行时编造数值。
- 字段级连接映射和转换说明，用于表达哪些输入产生某个下游输出。
- 每个节点都有输入与输出概览：输入字段按上游连接分组，输出字段归属于当前节点。字段名称、类型和可选示例值一并展示。点击输入来源可查看连接，点击输出字段可查看其直接下游字段映射。
- 每条连接都有传输元数据。可将连接标记为直接传递或 Redpanda；Redpanda 连接记录主题、消息键、载荷模式引用和具名消息头。已有连接在审阅之前保持未指定状态。
- 图视图、表视图和可编辑详情面板共享同一份持久化模型。
- 一键按依赖关系整理节点。使用图工具栏中的**整理节点**，调整卡片间距、适配画布并保存位置。
- 提供上游、下游、影响范围和有界上下文查询服务。
- 节点与连线写入校验、循环依赖检查，以及只追加的变更日志。
- 通过自然语言起草带有具名依赖的节点。配置 `OPENAI_API_KEY` 后，使用 OpenAI Responses API 和严格 JSON Schema；未配置密钥时，使用能力有限的本地解析器，使 MVP 仍可使用。两种方式都需要确认后才会应用变更。

如需使用模型生成草案，请在启动服务时设置环境变量 `OPENAI_API_KEY`。可通过 `OPENAI_MODEL` 选择模型，默认值为 `gpt-4o-mini`。API 请求会将草案提示词以及当前节点的名称和类型发送给 OpenAI，并设置 `store: false`。密钥保留在服务端。模型访问权限和费用由用户自己的 API 账户提供。集成遵循 [OpenAI 官方 Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs)。

架构决策和分阶段实施计划见 [实施计划](docs/IMPLEMENTATION_PLAN.md)。

应用维护的来源契约是期望上游输入的产品基线，不是已经采集到业务记录的证明。上游开放对象可能包含保存样本中尚未出现的字段。Few Understand 应实现该契约，并单独回报实际运行证据。启动时会退役未使用的 V2 记录类型节点；如果节点仍有设计连接或已匹配的数据需求，迁移会拒绝删除它。完成退役后，一次性迁移会让保留节点的引用编号连续，同时保持内部 ID 和图数据不变。此后的删除操作不会复用编号。修改上游契约后，应重新生成并审阅其修订版本，再交给 Few Understand。

设计新信号时，创建指标或评分节点，并在详情面板中定义结果。在**需要的数据**中列出产生该结果所需的输入，通过**去爬虫里找**搜索内置爬虫字段并匹配需求。未匹配的需求作为爬虫更新的待办保留；可展开的需求说明是供复制和讨论的草稿，不会自动发送请求或启动采集。

信号详情面板围绕四个问题组织：**这个信号想告诉我们什么**、**它需要哪些数据**、**如何计算和解释它**、**如何检验它**。记录验证计划和观察有助于设计；当前应用尚不会执行信号计算或回测。

加密信号平台的业务数据模型提案见 [资产模型](docs/ASSET_MODEL.md)。它仍是设计提案；该 MVP 尚未实现资产业务表和数据流水线。

同一份观察可以在图中描述两条路径：一条通向指标和信号事件，另一条通向拟议的资产身份或关系更新。证据检查和复核决策是用于覆盖情况检查，以及人工或策略审核的设计步骤。资产解析读取 `asset_identifiers` 和 `assets`，识别或绑定观察与结果；它可以位于资产级聚合之前，也可以位于按来源或市场计算的结果之后。关系查询在信号之后或产品视图之前读取 `asset_relationships` 和 `assets`。从表节点指向处理步骤的连线表示规划中的读取；指向表节点的连线表示拟议的更新。连线详情面板记录访问契约。由于图中的连线描述无环处理依赖，不应画出同一次运行中写回表的反馈环路。未来的执行系统会在每次运行时读取有版本的资产状态，并单独写入已审阅的更新。

用户与未来产品内信号助手的预期协作方式见 [产品工作流程](docs/PRODUCT_WORKFLOW.md)。Codex 项目指引见 [AGENTS.md](AGENTS.md)。当前的自然语言节点提案功能尚未实现该助手工作流程。

第一版有版本、可机器读取的信号执行包见 [信号执行契约](docs/SIGNAL_EXECUTION_CONTRACT.md)。运行一次 `python3 scripts/seed_example_signal.py`，将基于图的示例设计加入当前 SQLite 项目；之后通过 `GET /api/signals/coingecko_market_turnover_candidate/package` 可获取完整实施提案及其就绪检查。它仍是设计假设，没有已观察到的爬虫运行或经过验证的信号结果。

该执行包也将 Few Understand 标记为目标实施平台，将 Python + Polars 标记为优先考虑的计算技术栈。这些属于实施建议；信号定义中仍会明确要求的计算和输出，实施报告会记录实际选择的技术栈。

## 前端类型与 API 边界

前端正在迁移到 TypeScript，后端继续使用 Python。`src/contracts.ts` 通过 Zod 定义图数据和上游契约的接口模式，TypeScript 类型由这些模式推导。`src/api.ts` 在界面使用图数据和上游契约之前校验响应，包括图引用和字段归属。额外的服务端元数据会保留为未知类型的数据。

共享布局、引用编号、翻译、目录展示、来源用法，以及第一批字段、数据需求和导航组件已使用 `.ts` / `.tsx`。这些文件启用严格类型检查和索引访问检查。主入口 `src/main.jsx`、处理卡片以及其余案例与契约详情组件仍是 JavaScript，尚未接受类型检查（`allowJs: true`、`checkJs: false`）。应逐模块迁移；新增前端模块使用 TypeScript，避免使用 `any` 或屏蔽类型检查。检查通过不代表剩余 JavaScript 已获得类型覆盖，也不代表爬虫观察或信号效果已通过验证。

生产构建会先执行类型检查。GitHub 检查工作流运行下方相同的构建和回归检查。契约测试使用真实 Python 服务逻辑、临时 SQLite 数据库和保存的上游契约，不会修改项目数据。写操作响应、来源案例响应和信号执行包仍需在后续迁移批次中加入各自的类型校验器。
