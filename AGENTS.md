# SignalStudio development agent

Work with the user directly in Codex. Treat discussion as discussion; when the user asks for a change, implement it without adding process steps. Make routine technical decisions and keep changes small.

- Read only the code and documents relevant to the task. For signal-design behavior, use the relevant parts of `docs/PRODUCT_WORKFLOW.md` and affected contracts. New cards follow its **Card UI standard** section and the shared card components.
- Keep proposals, upstream examples, real crawler observations, and validated signals distinct. Declared fields in `catalog/raw-materials.v1.json` are not evidence of collected records.
- Run checks relevant to the change and report what changed, what passed, and what remains uncertain.
- Maintain the project documentation library proactively across all project conversations, not only metric research. Preserve meaningful product, design, architecture, data, development, and research discussions: requirements, definitions, decisions, rationale, alternatives, experiments, and open questions. Do not wait for the user to ask for documentation each time. Update the relevant existing document; use `docs/research/` for exploratory topics without an established home and keep its index current. Record substantive outcomes rather than transcribing every chat or creating duplicate notes. Clearly distinguish user-accepted decisions from proposals and verified findings, and retain dated reasons when decisions change. Discussion authorizes documentation under this standing instruction, not implementation or changes to execution contracts. Respect any explicit request not to record a discussion.
- By default, create a Git commit and push it to the current branch on GitHub after each completed, verified batch of changes so the work is traceable and available remotely. Stage only the files belonging to that work, use a descriptive commit message, and report the commit hash and push result. Skip committing or pushing when the user explicitly requests it. Do not force-push.
- Record tasks arising from future discussions in the user's Notion [Task Center](https://app.notion.com/p/3f3038a63d5a81ada8defaed0a6844b6), using data source `3f3038a6-3d5a-800d-b0b8-000bbc8e4236`. Read its current schema and check for an existing task before writing; update the same task as work progresses. Confirmed work is `待办`; tentative tasks are `待确认`. Do not invent owners, priorities, or deadlines. Keep a concise task summary, acceptance criteria, and verification/results in the task page. Link existing repository documents with GitHub URLs and repository-relative paths; short standalone text may live directly in Notion. Maintain one primary home for each full text instead of duplicating it. Preserve the documentation and evidence distinctions above. If Notion is unavailable, retain the task details locally and report the pending sync rather than claiming it was recorded.
- Leave unrelated work intact. Do not merge or publish deployments unless the user asks.
- A future in-product assistant must use application-owned instructions and saved project state; this file only guides Codex.
