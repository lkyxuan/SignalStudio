# SignalStudio development agent

Work with the user directly in Codex. Treat discussion as discussion; when the user asks for a change, implement it without adding process steps. Make routine technical decisions and keep changes small.

- Read only the code and documents relevant to the task. For signal-design behavior, use the relevant parts of `docs/PRODUCT_WORKFLOW.md` and affected contracts. New cards follow its **Card UI standard** section and the shared card components.
- Keep proposals, upstream examples, real crawler observations, and validated signals distinct. Declared fields in `catalog/raw-materials.v1.json` are not evidence of collected records.
- Run checks relevant to the change and report what changed, what passed, and what remains uncertain.
- Repository prose is the development reference: keep confirmed requirements, precise behavior/contracts, implementation status, setup, and verification instructions in Git. Put exploratory alternatives, ambiguous requirements, unresolved design discussions, and their history in Notion; link them rather than maintaining a second discussion body. Once a decision is accepted and ready to guide development, translate it into precise repository requirements/contracts with a link to its Notion rationale. Distinguish required behavior from implemented and verified behavior. Explicitly retain factual unknowns, unverified coverage, and current limitations where developers need them; never turn uncertainty into a definite claim merely to make documentation look authoritative. This boundary is user-confirmed on 2026-10-09; existing technical documents still require review before claiming they all conform.
- Maintain meaningful discussion records in Notion, the primary editable home for product, design, architecture, data, development, strategy, and research discussions (user decision 2026-10-09). Preserve requirements, definitions, decisions, rationale, alternatives, experiments, and open questions; distinguish user-accepted decisions, proposals, observations, and verified findings. Retain dated reasons when decisions change. Discussion authorizes recording, not implementation or changes to execution contracts. Respect explicit requests not to record. Do not append new discussion prose to repository Markdown; `docs/research/` now contains migration links. Code, executable contracts, and implementation-coupled technical instructions remain versioned in Git.
- By default, create a Git commit and push it to the current branch on GitHub after each completed, verified batch of changes so the work is traceable and available remotely. Stage only the files belonging to that work, use a descriptive commit message, and report the commit hash and push result. Skip committing or pushing when the user explicitly requests it. Do not force-push.
- At the start of each substantive discussion or work item, find and read the existing card in the user's Notion [研究中心](https://app.notion.com/p/3f3038a63d5a81ada8defaed0a6844b6), data source `3f3038a6-3d5a-800d-b0b8-000bbc8e4236`; create a card before proceeding if none exists. Read the current schema and check for duplicates. Continue the same strategy/research card across chats, and split independently actionable outcomes into linked child tasks (`父任务` / `子任务`). Keep goal, accepted decisions, work completed, remaining questions/actions, next step, completion criteria, and dated evidence/results current in the card. Use `明晰度=待澄清` for unclear work and `可执行` only when an actionable next step is defined; confirmed queued work is `待办`, active work is `进行中`, unresolved proposals are `待确认`, and deferred work can be `暂停`. Update the card before ending each meaningful batch; do not mark a strategy complete merely because the conversation or documentation is complete. Do not invent owners, priorities, deadlines, progress percentages, or source chat URLs. Preserve known source and output links. Discussion history belongs in the corresponding topic cards; find them through the research center database and card relations rather than maintaining a separate history/index page. If Notion is unavailable, keep a clearly labeled pending-sync local record and report it; never claim a write succeeded or maintain it as a second main copy.
- Leave unrelated work intact. Do not merge or publish deployments unless the user asks.
