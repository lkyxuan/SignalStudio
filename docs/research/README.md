### 2026-10-09：整体工作系统选择 Notion 或 Obsidian（讨论中）

用户进一步澄清：SignalStudio 只是代码库，考虑将内容集中到 Notion，并以多个数据库管理日常任务、研究等整体工作；同时希望重新比较 Obsidian + MD。该表述是方向探索，本轮未批准或执行全量迁移。

核对官方资料：Notion 支持数据库关系与汇总；Obsidian Bases 可直接基于本地 Markdown 与属性形成数据库式视图，并非只能写散文笔记。Notion 支持导出，但关系导出到 CSV 会变为文本 URL，不能把导出等同于完整可恢复的工作系统。Notion API 有请求速率和大小限制。

助手判断与建议：若主要目标是集中管理任务、项目、研究主题与资料，并减少自行维护界面和规则的负担，当前更倾向 Notion；若本地文件所有权、离线写作、可审阅文本差异和脚本批量操作是首要要求，则更倾向 Obsidian + MD。任务库可以通过类型与视图区分日常、研究、开发任务，不必按场景复制多个任务库；研究主题和来源资料是与任务不同的对象，可按实际需求建立关联库。个人工作与知识后台不同于应用运行数据后台，行情、爬虫原始记录、评分流水等不建议放进这两种工具作为主存储。每份正文只设一处可编辑主本；只读导出备份不构成第二套事实。建议先用一个真实研究主题验证资料→结论→任务→结果的闭环，再决定迁移；该试验尚未执行。

资料：[Notion 关系与汇总](https://www.notion.com/help/relations-and-rollups)、[Notion 导出](https://www.notion.com/help/export-your-content)、[Notion API 限制](https://developers.notion.com/reference/request-limits)、[Obsidian Bases](https://obsidian.md/help/bases)、[Obsidian 数据存储](https://obsidian.md/help/data-storage)。剩余问题是“整体后端”是否还包括应用运行数据，以及本地可控性与开箱即用管理的优先级。

### 2026-10-09：研究工作台的范围与认知负担

用户明确需要承接策略讨论、日常 Research、代币研究、项目笔记和看到的新闻；同时担心托管工具不够自由、自建或过度自由又增加脑力负担。助手建议（未批准实施）：先以 Notion 承载这些人工尺度的内容与关联，限制日常入口与必填字段，避免一开始搭建庞大的标签和数据库体系。候选入口为收集箱、研究台、行动清单；收集时只保存内容或链接，可选补充关注理由，整理时再关联代币、项目或研究主题。来源事实、个人判断、待验证假设应可区分，新闻不自动生成任务。

## 现有规则与证据边界

用户描述的旧前端 v1：heat 为注意力百分比×1.6、信号严重度之和×2.5、最高新闻重要性×34、信号条数×5、新闻条数×4、指标条数×2之和，截断到1–99。delta依次取注意力变化百分比、价格涨跌百分比、成交量变化÷10、多空信号数之差×2.5。

阶段按风险、分歧、爆发、降温、新出现及剩余方向依次判定。风险信号优先；多空都有且条数差≤1、证据≥3为分歧；delta≥8且heat≥55为爆发；delta<−1且heat≥40为降温；45分钟内刚出现、6小时窗口内且证据≤2为新出现。升温按delta、最热按heat、新出现按出现时间、降温按delta升序、分歧及风险按heat排名，证据窗口48小时。这是用户提供的规则描述，本轮未审计旧前端代码。

本仓库现有 [产品流程](../PRODUCT_WORKFLOW.md) 和 [业务表定义](../BUSINESS_TABLES.md) 仍定义演示版 total_heat：首次建档贡献100，7天半衰期，事件衰减后求和。文档说明计算器与真实评分流水尚未运行。本轮确认本地工作台与图数据API可访问，不代表榜单计算已运行。

## 共同候选设计

以下均为助手在2026-10-07提出的草案，用户尚未接受公式或参数：

- 共享带来源与时间的事件证据，五榜独立计算；允许跨榜出现，合格候选不足时不强凑50名。
- 有效讨论权重 w = 资产相关度 × 可信度 × 重要性权重。重要性可先试1、1.5、2；相关度与可信度的量表仍待定义。
- 聚合同一新闻的转载；独立观点可另计，同作者刷屏设上限。消息和由它触发的告警不重复贡献。
- 区分信息发布时间与采集时间；回放只能使用当时已收到的信息。
- 缺失不等于零，数据源断采不等于降温。来源覆盖变化需要单独记录。
- 价格、成交量作为市场背景，不替代注意力变化。Kaito等外部注意力数据不是默认免费可持续输入。
- 建档不代表市场关注；建议让建档+100退出正式热度，尚未修改原契约。

优先接入持续可采的原创公告、论坛、博客/RSS与公开讨论，并建立资产身份映射。公开行情用于解释与验证，扩大社交覆盖在后续进行。可参考 [Binance公开行情](https://developers.binance.com/en/docs/products/spot/rest-api)、[DEX Screener接口](https://docs.dexscreener.com/api/reference)、[Kaito PAYG说明](https://github.com/MetaSearch-IO/KaitoX402APIDocs)。接口可读、免费额度、商业使用条件与实际爬虫覆盖应分别确认，不能把接口文档当作采集记录。

## 共同验证方法

积累连续数据后按历史到达时间重放。每天抽查各榜前10及未入榜候选，检查误报和漏报；比较不同窗口和阈值的稳定性。先验证榜单是否准确描述关注状态，再补充未来价格表现，不能用收益率替代所有榜单的目标。

目前没有这五套候选规则的实验或回测结果。主要待改问题是delta语义混用、证据重复加分与截断、阶段优先级代替独立榜单定义。

## 2026-10-08：五榜与共享 Redis、评分表的关系（架构讨论，未批准实施）

用户询问五榜是否需要五个 Redis，以及升温/降温/最热是否只是同一个热度数的不同筛选。核对现有研究草案后，区分如下：当前 #6001 → #3005 → #1006 只定义 total_heat 演示链路（建档 +100、7 天半衰期），不是五榜的完整算法。#1006 可按 asset_id + score_key 容纳多个指标的当前值，但其当前分不能代替历史快照，也不能凭单个热度值推出观点分歧或首次出现。

助手建议：先共享一个 Redis 服务，不因五榜而创建五套 Redis 实例；按用途、指标和时间窗口分开键空间，共用可复用证据，分别保存必需的历史/聚合状态。逻辑数据集不等于独立物理 Redis，#6001 当前的原始评分事件契约也不会自动提供其他榜所需的原文、观点方向、首次发现和历史基线。只有独立容量、性能或隔离要求有证据时再考虑拆分实例。本轮未修改 Redis 或执行契约。

五榜仍需各自定义：最热看当前关注规模；升温看近期关注相对历史增长；降温看此前高位到当前的回落；新出现看首次有效发现/出现时间及证据；分歧看可比较议题的多空观点。最热、升温、降温可复用基础热度或贡献时间序列，但升温/降温不等于对当前热度简单正反排序。示例：两个资产当前均 80，一个此前 40、另一个此前 100，变化方向不同。现有草案还要求区分正常衰减、来源断采与真正关注退潮；公式、窗口和资格仍待用户确认，不将示例差值直接作为正式规则。

若以后实施五榜，可用同一当前评分表、不同 score_key 表示五种结果，按指标分别选榜；历史窗口、资格、计算时间及参数版本需另明确。当前 #3010 只以 total_heat 前 100 筛选，不能原样用于其他榜，否则会漏掉热度不高但升温很快的资产。未来需对各榜分别判断资格并按相应指标同步，或为各榜定义独立模块；这只是扩展建议。早期研究的每榜前 50 与当前热度演示前 100 属于不同阶段，未据此把其余四榜改成 100。#1007 的 3 分钟有效期也不能未经校验直接套用到更新更慢的指标。

## 2026-10-08：Redis 数据区不等于 Redis Streams

用户询问当前 Redis 使用方式是否为 Stream。核对本仓库：新增五榜骨架的 `redis_type` 均为 null，尚未选型；现有 #6001 卡片声明缓存有效评分事件，未声明 Streams。已有[集成记录](../FEWUNDERSTAND_INTEGRATION.md)引用 fewunderstand 的 `common/asset_score/redis_projection.py`，其实现参考使用 `{prefix}:{generation}:events` Hash，由 `:active` 指向 generation；这是先前代码核对记录，本轮没有重新访问远端代码或运行 Redis 检查。

概念澄清：Redis Streams 是追加事件、按进度消费的日志结构；Hash 可按事件 ID 存取记录；Sorted Set 可存资产与分数并按分数排序。持续收到数据或定时重算，不自动意味着采用 Redis Streams。现有设计将消息传输放在 Redpanda，Redis 承担计算所需状态缓存，因此不必仅因“实时”再增加一层 Stream。Sorted Set 仅为未来保存有序结果时的候选，不是本轮选型决定。参考 [Redis 数据类型比较](https://redis.io/docs/latest/develop/data-types/compare-data-types/)。本轮仅澄清概念，未修改执行契约或部署。


## 2026-10-09：Redis 必须有退出规则，不能靠选 Stream 代替生命周期设计

用户明确提出持续写入而无退出不可接受，并询问 Stream 是否因此优于 Hash。这是容量与生命周期要求，尚未批准改用 Stream 或某个具体清理阈值。现有五榜骨架的 retention 仍为 null；#6001 要求保留有效贡献或等价状态，但尚无完整退出实施方案。

助手建议继续用 Hash 承担按事件 ID 查询、去重及评分计算状态，Redpanda 承担消息流；若以后需要 Redis 自己管理顺序消费与消费进度，再考虑 Streams。Stream 的 MAXLEN/MINID 裁剪需要主动配置或执行，并不自动理解业务贡献是否失效；时间裁剪按 Stream ID，不能把补采入流时间当成原始事件时间。Hash 同样可以逐字段 HDEL；Redis 7.4 起支持字段 TTL，但实际服务版本未核验，不能依赖整张 Hash 的 EXPIRE 代替每条记录的生命周期。参考 [XTRIM](https://redis.io/docs/latest/commands/xtrim/) 与 [HEXPIRE](https://redis.io/docs/latest/commands/hexpire/)。

待讨论的退出方案：固定窗口算法可在超窗且不再被其他计算需要后清理；指数衰减算法需另定义截断和可接受误差，或在满足线性可加且同一衰减策略等条件下合并为等价状态。7 天半衰期意味着原 100 分剩 50 分，不是过期；未经批准不能裁剪成零。删除前需保证约定的持久归档/恢复依据可用，清理后重放也不能使旧事件重复加分；清理任务、重试、索引一致性和容量监控后续补齐。资产出榜、前端显示过期与原始贡献退出 Redis 是不同事项。以上是助手建议，未修改卡片执行契约、实际 Redis 或算法。


## 2026-10-09：按信息种类区分半衰期与贡献截止时间

用户进一步提出不同种类的信息传播时间不同，询问何时基本没有传播效力、是否应有删除时间。记录该设计方向；用户尚未选择具体半衰期、截止比例或最大期限。现有系统没有已确定的删除时间。

助手解释：纯指数衰减在数学上不会于有限时间归零。经过 4、5、7 个半衰期分别剩 6.25%、3.125%、0.78125%；达到 5% 和 1% 分别需约 4.322 和 6.644 个半衰期。这只是现有模型的数值，不是实际传播终止的观测。当前演示 H=7 天，7H=49 天也仅为推算，建档 +100 的参数不是经测量的信息传播周期。

候选设计是按“信息类别 × 评分规则”分别定义半衰期与贡献截止期限；可讨论以 5–7 个半衰期作为实验起点，但尚未接受或验证。也需评估初始权重和累计被截断贡献，不能认定每条小于 1% 就一定对总分无影响。截止后停止贡献与物理删除分开：先更新计算结果，满足其他消费者及归档/恢复需求后再清理缓存，保留必要去重依据。后续真实新传播/进展可按规则产生新贡献，重复采集不能续命。

要确定真实传播期限，应采集各类信息随时间新增的独立提及/互动与来源覆盖，观察增量何时回到基线，区分断采与冷却，再校准参数。研究 [Novelty and Collective Attention](https://arxiv.org/abs/0704.1158) 讨论特定网站上的关注衰减；[Accelerating dynamics of collective attention](https://www.nature.com/articles/s41467-019-09311-w) 讨论跨领域关注周期变化，均不能提供本项目各类加密信息的通用删除期限。未修改算法、执行契约或 Redis。
