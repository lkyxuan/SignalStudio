# Signal research workflow

## What the user is responsible for

The user brings a business question, a project or asset worth investigating, a post or page to examine, or an example of a useful result. They judge whether the proposed output matches what they want to find. They do not need to choose crawler fields, design tables, specify joins, or invent formulas before the system can help.

The product should accept rough inputs such as “find projects that are starting to get attention” or “explain what this author is doing and whether we can reproduce the method.” A link, pasted text, or named project can start the investigation.

## Assistant workflow

1. Restate the desired finding in ordinary language and identify the entity and time horizon only as far as the example supports.
2. Propose a small number of testable signal ideas. For each, explain what would count as evidence, what could cause a false positive, and what the output would look like.
3. Inspect the application-owned upstream source contract first, then compare crawler implementation and returned records when available. Select identity, time, measurement, and provenance fields internally; identify missing inputs explicitly. A field definition is not proof that observations exist.
4. Draft the necessary data mapping, aggregation, deduplication, calculation, and validation plan. Show these technical details on demand for review, without requiring the user to supply them.
5. When real records and execution are available, run a small sample, show concrete results and source evidence, then revise with the user. Until then label the work as a design hypothesis.
6. Save accepted definitions and decisions to project state so future sessions can resume without relying on chat history.

The first screen of a future product assistant should ask “What do you want to find?” and allow an example or link. It should return candidate approaches and evidence gaps before presenting a field-by-field editor. A crawler can contain several record types; display fields under their record type and distinguish measurements from identifiers, timestamps, provenance, and raw payloads.

In each source node's detail panel, show paired observed input and response examples first, with a short natural-language explanation of what that whole call found. When the API returns a daily series, show every observed day in the example; if the requested and returned ranges differ, say so. Show contrasting parameter combinations for operations with materially different query modes. Keep parameter definitions, per-field cards, original paths, provenance, and documentation in a collapsed technical section after the examples. Label examples as upstream responses, not crawler observations. If no paired call is available, state why and do not assemble a fictitious pair from parameter definitions and independent response samples. Keep the source-by-source audit in `docs/SOURCE_FIELD_AUDIT.md`. An observed sample inventory may omit fields from other rows or parameter branches; a redacted value is not an absent field.

## Card UI standard

Approved content refresh design (2026-10-10): one shared processing card consumes each of the
five existing boards' top N and refreshes content per asset and information type. The logical
content/state table and graph dependencies are installed from `catalog/content-refresh.v1.json`.
The card uses the shared processing frame, visible execution triggers, derived synthetic
branches and a separate empty observed result table. Defaults are top 20 per board, 30-minute
content refresh, commit/startup checks and a 60-second fallback. Runtime generators, storage,
frontend reads and notification/task bindings remain unconnected. Precise requirements and
verification are in [CONTENT_REFRESH_ENGINE.md](CONTENT_REFRESH_ENGINE.md), with the
[approved Notion rationale](https://app.notion.com/p/3f4038a63d5a8170b017f6615cf4af45).

The graph has connection lines, source cards, processing cards, transport and cache cards, and table cards. A line only connects cards and shows direction. A source card describes one upstream operation. A processing card represents one transformation or decision. A Redpanda Topic or Redis window card shows the data present in that channel or cache, together with its own topic/key/schema, Headers, retention, or recovery settings; it does not repeat input/output panels because the neighboring cards and lines show the route. A table card opens as a conventional horizontal table: exact backend field names across the top and one record per row. These are different views of the same flow, not interchangeable card layouts.

1. **Source and processing cards show input and output first, side by side.** Give both columns the same numbered field-row format, with field name and value or example. Name every input source node or table. On a processing card, show only the input fields relevant to its current calculation and output, and explicitly identify the subset. Link to source/table cards for complete fields and exploration of other algorithms; do not provide a full-record expansion inside the processing card. A source card still shows its operation’s input/output record.
2. **Then explain the source or step in plain language.** Show what this card does, what the selected case shows or how far processing has reached, and how to read the selected record. End the processing-card content with a read-only, natural-language algorithm explaining how those inputs yield the outputs. Card-specific short headings may vary. This is read-only explanatory text, not an empty form for the user to fill in.
3. **Table cards open with the raw table.** Keep the original columns and rows as the first and dominant element. Do not transpose the data into a vertical field list or add a display-only column to the raw table. Keep long JSON available inside its cell. Put record provenance and plain-language interpretation after the table. Put field meanings, types, primary keys, and required/nullable constraints behind Other settings. The backend field names in the header are the authoritative names. A table card does not show processing input/output panels; the source or processing card explains how a row was produced.
4. **Keep provenance visible in cases.** Use a real paired input/output case when one exists. If only an upstream input is observed, label the output as a planned format, not an executed result. Never turn a declared field, example value, planned table row, or unverified match into an observed result. Show the fields this step produces or uses for its output, distinguishing copied fields from newly generated fields. Do not expand unrelated pass-through payloads; preserve the complete execution schema on its owning source or storage card and in contracts.
5. **Collapse technical settings on source and processing cards.** Put editable purpose, generated implementation rules, error handling, classification, and evidence notes in Other settings. An upstream operation's Other settings displays its collection plan read-only. The user defines the cadence through AI; AI updates `catalog/source-collection-plans.v1.json` and rebuilds `catalog/source-contracts.v1.json`. The generated operation contract carries the mode and interval in minutes for the implementing system. Leave these unset until a cadence is chosen; a query's historical time window is not its collection interval, and a saved plan is not evidence that a crawler ran at that frequency. Redpanda topic, Headers, message key, and consumer groups belong on the Topic card. The processing card describes parsing, computation, and output.

This is a different presentation of the saved graph, not an additional node, edge, or execution trace. The full graph remains available for spatial overview and editing.

In the full graph, connections use curved routes and separate attachment points on cards; specified table writes attach below the cards. Hovering or selecting a card emphasizes its direct neighbors. Decision styling marks the #4001 lookup and other review decisions. #4001 route labels describe the branch conditions; the saved case supplies real source values and specified results for the first lookup, paired table rows, and repeated input. Curves improve readability without guaranteeing that all crossings disappear.

Every saved graph card has a four-digit reference shown on the card, table row, and detail panel: `#1xxx` for business tables, `#2xxx` for upstream operations and reference resources, `#3xxx` for processing programs and outputs, `#4xxx` for checks and decisions, including rule evaluation and branch-routing lookup, `#5xxx` for Redpanda Topic cards, and `#6xxx` for Redis window cards. An asset or relationship lookup can be classified as a program or a decision when created. Within each group, assign numbers from 1 in the order cards are created. Search accepts a full reference or a group prefix such as `#2`. The one-time migration of existing cards keeps their internal IDs, fields, connections, and internal L/R references; saved prose references are updated to the new numbers. After migration, numbers persist across renames and layout changes and are not reused after deletion.

For a source whose name alone does not explain its use, show a short purpose on the card and a concrete input → expected output → next processing step explanation in its detail panel. Label examples as illustrative and distinguish observed upstream API fields from crawler records and deployed processing. A source node is a record-type design reference, not an interactive query form.

## Crawler input and output understanding

Maintain the application-owned, versioned contract in `catalog/source-contracts.v1.json` for each desired upstream operation. Few Understand consumes it to implement crawlers and reports implementation status and real emitted records separately; it does not define desired source fields for this product. The assistant should record the user-facing purpose; required and optional inputs with meanings, accepted values and defaults; an ordinary-language example and its resolved parameters; output record types and key fields; one clearly labeled response example; provenance; and the next useful processing step. Track separately whether each item comes from an upstream API sample, crawler code or fixture, observed crawler run, or design hypothesis. Unknown parameters and unverified output mappings must stay explicitly unknown. A declared output field or test fixture is not evidence that a crawler has emitted that record in production.

When a user describes a need in natural language, the assistant identifies the subject, time range and intended question, selects a candidate operation, and shows the proposed input interpretation before any future execution. It then explains returned records as concrete business objects with source evidence and validation status. If the input contract is incomplete, it describes the intended query and missing contract instead of inventing exact API parameter names or claiming it can run. Persist accepted interpretations and contract revisions in project state so later sessions can use them.

For `kaito.mcp.kaito_events`, explain that a source event is a candidate occurrence or catalyst with references.
