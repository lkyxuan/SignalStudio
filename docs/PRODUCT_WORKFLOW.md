# Signal research workflow

## What the user is responsible for

The user brings a business question, a project or asset worth investigating, a post or page to examine, or an example of a useful result. They judge whether the proposed output matches what they want to find. They do not need to choose crawler fields, design tables, specify joins, or invent formulas before the system can help.

The product should accept rough inputs such as “find projects that are starting to get attention” or “explain what this author is doing and whether we can reproduce the method.” A link, pasted text, or named project can start the investigation.

## Assistant workflow

1. Restate the desired finding in ordinary language and identify the entity and time horizon only as far as the example supports.
2. Propose a small number of testable signal ideas. For each, explain what would count as evidence, what could cause a false positive, and what the output would look like.
3. Inspect the application-owned upstream source contract first, then compare crawler implementation and returned records when available. Select identity, time, measurement, and provenance fields internally; identify missing inputs explicitly. A field definition is not proof that observations exist.
4. Draft the necessary data mapping, aggregation, deduplication, calculation, and validation plan. Show these technical details on demand for review, without requiring the user to supply them.
5. When real records and execution are available, run a small sample, show concrete results and source evidence, then revise with the user. Until then label the work as a design hypothesis.
6. Save accepted definitions and decisions to project state so future sessions can resume without relying on chat history.

The first screen of a future product assistant should ask “What do you want to find?” and allow an example or link. It should return candidate approaches and evidence gaps before presenting a field-by-field editor. A crawler can contain several record types; display fields under their record type and distinguish measurements from identifiers, timestamps, provenance, and raw payloads.

In each source node's detail panel, show the application-owned upstream contract first, with one compact card per field: name, concrete data, and how to use it. Keep original paths in hover text and link a field to its official documentation or saved API/MCP sample. Put a design idea after the field list. Label sample values as upstream responses, not crawler observations. Keep the source-by-source audit in `docs/SOURCE_FIELD_AUDIT.md`. An observed sample inventory may omit fields from other rows or parameter branches; a redacted value is not an absent field. Put field cards near the top of the panel so a long node overview does not hide them.

## Design graph organization

Kaito's `kaito://tokens` and `kaito://narratives` are MCP reference resources, not database tables or `kaito_entities` / `kaito_narratives` tool calls. Show them as separate Source references in the graph, with their resource URIs and identity-lookup purpose. Do not imply their contents were crawled or infer response fields before a resource read is verified.

The design workspace distinguishes data sources, processing steps, business tables, and outputs. The app-owned `catalog/source-contracts.v1.json` defines desired upstream operations. A source can offer many operations and record types. Each upstream operation has its own Source node. Unused V2 record-type Source nodes are retired; connected designs require review before removal. The app-owned contract is the product baseline for desired upstream fields. Each planned business table (`assets`, `asset_identifiers`, `asset_relationships`, `asset_monitoring_rules`) is a distinct graph node so a dependency names the exact table a future program must read or update. These are design references, not deployed tables or individual rows. Asset Resolution reads `asset_identifiers` and `assets` to bind observations or results to an internal `asset_id`. A later Relationship Lookup reads reviewed `asset_relationships` and `assets` after a signal or while preparing a product view; a relationship does not itself validate or trigger a signal. Rule Evaluation reads `asset_monitoring_rules`. The same saved graph has Overview, Signal path, and Asset knowledge path views. Assign a step to one path or both; shared source and identity steps need not be duplicated. A knowledge proposal must be reviewed before it changes tables used by later runs. A complete design graph still does not establish that crawled observations or validated signals exist.

Redpanda edges describe message transport between programs. A table edge describes a direct, planned backend read or reviewed write, with lookup keys and result expectations recorded on the connection. The browser should receive a backend response containing the related assets; it should not query these tables directly. Overview opens the single complete saved graph, including unconnected upstream operations and planned business tables. Fit the canvas to that full map on entry; users can zoom, search, and filter by path or type. The table view lists current upstream operations alongside designed nodes. Signal path and Asset knowledge path are filters over that same graph. The application does not pre-create processing steps or read/write edges from examples. Source details can count designed direct destinations and downstream nodes, but a trace for a specific crawled record requires execution lineage: a stable observation/message ID, processing run and version, Redpanda topic/offset or equivalent source position, generated result IDs, and recorded fan-out. No database queries, Redpanda consumers or record-level traces are implemented by a graph connection.

For a versioned signal, selecting its Redpanda line should show only what the producer plans to put on that topic: message envelope and key, every declared upstream field path inside the payload, metadata fields, and evidence status. The downstream node owns the smaller set of consumed message paths, field mappings, calculation, trigger, and output. Keep these as separate machine-readable line and processor contracts in the exported package. Mark upstream field inventory as a contract lower bound and the message envelope as a plan until real emitted messages are reported. The line reference identifies a design handoff; it cannot show a particular record's journey without execution lineage.

The Arrange nodes action keeps connected dependencies left to right. Unconnected upstream operations are packed into compact blocks by source, and unconnected business tables form their own block. The source and table headings are visual labels, not additional saved graph nodes or relationships.

Every saved graph node has a short reference such as `#006`, shown on its card, table row, and detail panel. People can use this reference when discussing a node or searching the graph. The one-time cleanup of retired V2 nodes compacts the surviving references after those nodes have been removed, while preserving each node's internal ID, fields, and connections. After that cleanup, references persist across renames and layout changes and are not reused after future deletions.

For a source whose name alone does not explain its use, show a short purpose on the card and a concrete input → expected output → next processing step explanation in its detail panel. Label examples as illustrative and distinguish observed upstream API fields from crawler records and deployed processing. A source node is a record-type design reference, not an interactive query form.

## Crawler input and output understanding

Maintain the application-owned, versioned contract in `catalog/source-contracts.v1.json` for each desired upstream operation. Few Understand consumes it to implement crawlers and reports implementation status and real emitted records separately; it does not define desired source fields for this product. The assistant should record the user-facing purpose; required and optional inputs with meanings, accepted values and defaults; an ordinary-language example and its resolved parameters; output record types and key fields; one clearly labeled response example; provenance; and the next useful processing step. Track separately whether each item comes from an upstream API sample, crawler code or fixture, observed crawler run, or design hypothesis. Unknown parameters and unverified output mappings must stay explicitly unknown. A declared output field or test fixture is not evidence that a crawler has emitted that record in production.

When a user describes a need in natural language, the assistant identifies the subject, time range and intended question, selects a candidate operation, and shows the proposed input interpretation before any future execution. It then explains returned records as concrete business objects with source evidence and validation status. If the input contract is incomplete, it describes the intended query and missing contract instead of inventing exact API parameter names or claiming it can run. Persist accepted interpretations and contract revisions in project state so later sessions can use them.

For `kaito.mcp.kaito_events`, explain that a source event is a candidate occurrence or catalyst with references. It is different from a downstream `Signal Event`, which would be emitted only after a versioned rule evaluates evidence. The contract has a small MCP response sample, but no verified crawler run for this operation.

The current `kaito-social-spider` implementation calls `kaito_events` with `entity`, `window`, and `limit`; its configured defaults are `next_14d` for the event window and 50 for the candidate limit. The entity comes from candidate discovery or a configured watchlist. This is evidence of how crawler code forms a request, not proof that the upstream API accepted a particular call or that a production crawler message exists. Natural language is a future assistant interface that would resolve a user's project and time request into supported parameters; the upstream operation node itself is not that interface.

`kaito.mcp.kaito_search` and `kaito.mcp.kaito_advanced_search` are separate upstream operations, not search boxes in the current canvas. The current crawler automatically calls `kaito_advanced_search` for candidate entities with structured filters. Design material describes `kaito_search` as natural-language search, but the crawler does not currently call it. The assistant should name the operation that produced a result and explain its actual input contract.

Every saved connection has its own permanent `L` reference, such as `L001`, shown on the line and in connection details. Every field usage within a connection has a separate permanent `R` reference, such as `R001`, shown beside that mapping. Search accepts all three kinds of references; searching for a line or field usage shows its endpoint nodes and line. Numbers are assigned once, survive edits and rearrangement, and are not reused after deletion. These identify saved design objects, not observed crawler records.

## Multi-agent option

When an investigation benefits from parallel perspectives, one agent can propose candidate methods, one can check them against available data, and one can challenge assumptions and likely false positives. A coordinating assistant should reconcile their findings into a short, reviewable proposal. Multiple agents are an implementation option, not a requirement for the user to operate the product.

## Where this guidance lives at runtime

This document is the product specification. `AGENTS.md` gives Codex project guidance when working in this repository. Neither file is automatically applied to an AI embedded in the web page. When that assistant is built, keep its versioned instructions in server-side application code, load the current crawler catalog and saved project decisions as request context, and persist conversation or research state across sessions. Do not depend on the user's Codex conversation as the product's memory.

The current app supports catalog browsing and drafting graph nodes and connections. Its natural-language proposal only drafts a node with dependencies. It does not yet inspect posts, orchestrate research agents, run signal calculations, or store a product-assistant conversation.

A signal execution package separates required behavior (source inputs, calculation, trigger, output and evidence) from preferred implementation technology. Mark the target platform and suggested products or components, such as Polars for a calculation in Few Understand, as design guidance with an explicit verification status. The implementing platform chooses the actual component and reports that choice and any deviations. Finding a library or processor in its repository is code evidence, not proof that this signal has run on it.
