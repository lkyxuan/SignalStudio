# Signal research workflow

## What the user is responsible for

The user brings a business question, a project or asset worth investigating, a post or page to examine, or an example of a useful result. They judge whether the proposed output matches what they want to find. They do not need to choose crawler fields, design tables, specify joins, or invent formulas before the system can help.

The product should accept rough inputs such as “find projects that are starting to get attention” or “explain what this author is doing and whether we can reproduce the method.” A link, pasted text, or named project can start the investigation.

## Assistant workflow

1. Restate the desired finding in ordinary language and identify the entity and time horizon only as far as the example supports.
2. Propose a small number of testable signal ideas. For each, explain what would count as evidence, what could cause a false positive, and what the output would look like.
3. Inspect the application-owned upstream source contract first, then compare crawler implementation and returned records when available. Select identity, time, measurement, and provenance fields internally; identify missing inputs explicitly. A field definition is not proof that observations exist.
4. Draft the necessary data mapping, aggregation, deduplication, calculation, and validation plan. Show these technical details on demand for review, without requiring the user to supply them.
5. When real records and execution are available, run a small sample, show concrete results and source evidence, then revise with the user. Until then label the work as a design hypothesis.
6. Save accepted definitions and decisions to project state so future sessions can resume without relying on chat history.

The first screen of a future product assistant should ask “What do you want to find?” and allow an example or link. It should return candidate approaches and evidence gaps before presenting a field-by-field editor. A crawler can contain several record types; display fields under their record type and distinguish measurements from identifiers, timestamps, provenance, and raw payloads.

In each source node's detail panel, show paired observed input and response examples first, with a short natural-language explanation of what that whole call found. When the API returns a daily series, show every observed day in the example; if the requested and returned ranges differ, say so. Show contrasting parameter combinations for operations with materially different query modes. Keep parameter definitions, per-field cards, original paths, provenance, and documentation in a collapsed technical section after the examples. Label examples as upstream responses, not crawler observations. If no paired call is available, state why and do not assemble a fictitious pair from parameter definitions and independent response samples. Keep the source-by-source audit in `docs/SOURCE_FIELD_AUDIT.md`. An observed sample inventory may omit fields from other rows or parameter branches; a redacted value is not an absent field.

## Design graph organization

Kaito's `kaito://tokens` and `kaito://narratives` are MCP reference resources, not database tables or `kaito_entities` / `kaito_narratives` tool calls. Show them as separate Source references in the graph, with their resource URIs and identity-lookup purpose. Do not imply their contents were crawled or infer response fields before a resource read is verified.

The product workspace distinguishes sources, processing steps, business tables, and outputs. The six active business table contracts are `assets`, `asset_identifiers`, `asset_relationships`, `asset_monitoring_rules`, `asset_score_events`, and `asset_scores_current`. `assets` is the internal asset map: each row has a stable `asset_id` and a current `name` that may temporarily come from a newly observed X account. `identity_status` says whether the object's identity has been resolved; `asset_kind` says what kind of object it is. The first #1001 contract has only five fields: `asset_id`, `name`, `identity_status`, `asset_kind`, and system-managed `created_at`. A review reference and more audit fields remain for later review-flow design. `asset_identifiers` has exactly three fields: `source_namespace`, `external_identifier`, and the referenced #1001 `asset_id`. One row maps one source-scoped external ID to an internal asset. The portable schemas are in `catalog/business-tables.v1.json`; `docs/BUSINESS_TABLES.md` explains the table contracts and case rows. The retired candidate-group path stays retired because unmatched accounts now enter #1001 and #1002 immediately. `asset_relationships` and `asset_monitoring_rules` remain separate later-stage tables. `asset_score_events` records deduplicated score contributions after each producer saves a durable detailed decision; its single `decision_ref` points back to the producer and record ID. The proposed score event would enter a Redpanda Topic only after fewunderstand approves and creates it; independent consumer groups would then maintain Redis score events and archive the full #1005 ledger in Delta/Parquet. The Redis path does not wait for the archive. For this demo, `asset_scores_current` is the Redis-backed current view of one metric, `total_heat` (overall heat), per asset. Rank is derived at query time. Neither score table has observed rows or a running calculator yet.

The planned score route is #3006 score-event publisher → #5001 proposed Redpanda Topic → two independent consumers: #3007 maintains #6001 Redis score events and #3008 archives #1005 in Delta/Parquet. #3005 reads #6001 and updates #1006. The demo uses a single score key, `total_heat`: #3009 contributes +100 once on first asset creation; later scoring rules may contribute to the same key with their own immutable decay policies. At a fixed UTC time, #3005 sums each event's `score_delta × 2^(-elapsed_minutes / event_half_life_minutes)`. The initial `asset_initial_score/v1` contribution has a seven-day (10,080-minute) half-life. Elapsed minutes since original UTC `created_at` may be fractional; seven and fourteen days are checkpoints at 50 and 25 points, not steps. Retain each still-active decaying event or equivalent per-policy state in Redis, not a uniform 24-hour TTL. Keep calculation and ranking values unrounded; display scores to two decimals. Query the current values at one common time, sort by score descending and `asset_id` ascending, and expose the result through a backend read API for the UI. Coalesce repeated triggers for the same asset and prevent older asynchronous calculations from overwriting newer results. The demo ranks all registered assets without an asset-kind or identity-status filter, so a pending social account can appear. The cards describe intended behavior only. No score event, Redis projection, aggregation job, ranking API, or completed calculation run exists yet.

## Card UI standard

The graph has connection lines, source cards, processing cards, transport and cache cards, and table cards. A line only connects cards and shows direction. A source card describes one upstream operation. A processing card represents one transformation or decision. A Redpanda Topic or Redis window card shows the data present in that channel or cache, together with its own topic/key/schema, Headers, retention, or recovery settings; it does not repeat input/output panels because the neighboring cards and lines show the route. A table card opens as a conventional horizontal table: exact backend field names across the top and one record per row. These are different views of the same flow, not interchangeable card layouts.

1. **Source and processing cards show input and output first, side by side.** Give both columns the same numbered field-row format, with field name and value or example. Name every input source node or table. When a step uses a complete record, show the complete record on its incoming connection and input panel; if it uses a subset, make that selection explicit.
2. **Then explain the source or step in plain language.** Show what this card does, what the selected case shows or how far processing has reached, and how to read the selected record. Card-specific short headings may vary. This is read-only explanatory text, not an empty form for the user to fill in.
3. **Table cards open with the raw table.** Keep the original columns and rows as the first and dominant element. Do not transpose the data into a vertical field list or add a display-only column to the raw table. Keep long JSON available inside its cell. Put record provenance and plain-language interpretation after the table. Put field meanings, types, primary keys, and required/nullable constraints behind Other settings. The backend field names in the header are the authoritative names. A table card does not show processing input/output panels; the source or processing card explains how a row was produced.
4. **Keep provenance visible in cases.** Use a real paired input/output case when one exists. If only an upstream input is observed, label the output as a planned format, not an executed result. Never turn a declared field, example value, planned table row, or unverified match into an observed result. Preserve the complete output schema and distinguish copied fields from fields added by this step.
5. **Collapse technical settings on source and processing cards.** Put editable purpose, generated implementation rules, error handling, classification, and evidence notes in Other settings. An upstream operation's Other settings displays its collection plan read-only. The user defines the cadence through AI; AI updates `catalog/source-collection-plans.v1.json` and rebuilds `catalog/source-contracts.v1.json`. The generated operation contract carries the mode and interval in minutes for the implementing system. Leave these unset until a cadence is chosen; a query's historical time window is not its collection interval, and a saved plan is not evidence that a crawler ran at that frequency. Redpanda topic, Headers, message key, and consumer groups belong on the Topic card. The processing card describes parsing, computation, and output.

Each defined flow should carry at least one concrete case that a person can follow across cards. When an upstream API is available, save the actual request and one or two actual returned records; state the full response count and the saved sample count separately. Use those records to specify the intended branch, output row, and table state in the product tool. Label actual upstream observations and specified downstream results separately. The product workspace is the contract for a separate implementing AI; it does not need a local Python processor or local database execution to define the behavior. Do not describe a specified empty table as evidence that a deployed business table has no matching row. Do not invent downstream approvals or confirmed assets to complete a story.

`src/ProcessingIOCard.jsx` implements the shared processing-card pattern. `src/BusinessTableCard.jsx` presents #1001/#1002 with two target rows based on real #2030 Kaito MCP account inputs, plus three named-asset rows in #1001 and five identifier or alias rows in #1002. #1003/#1004 each contain three rows defining their table formats. The intended first lookup, paired asset and identifier write, and repeated-input behavior are specified in `catalog/identity-flow-case.v1.json`. Those lookup and write outcomes have not been observed in a deployed backend; neither has a Redpanda message, AI naming, asset verification, or merge.

The #1002 Bitcoin case adds two proposed alias rows: `alias_name_zh=比特币` and `alias_ticker=BTC`. Both reuse the #1001 Bitcoin `asset_id`, alongside the existing `coingecko_coin_id=bitcoin` row. A ticker alone is not sufficient evidence to bind a previously unseen source record; ambiguous or conflicting names need source context and review.

#4001 has three labeled routes. An existing X ID in #1002 leads to #3004 and reuses its asset_id, even when the internal asset is still `pending_identity`. A missing X ID leads to #3002, which should write #1001 and #1002 as one operation. A broken or conflicting mapping stops automatic creation and goes to #4003 for review. The saved case specifies the missing-ID route and what a later repeated input must do; the backend has not executed these routes here.

The #2030 asset-map flow preserves one decision or state change per card. #4001 compares the stable X user ID, never a mutable display name. #3002 defines creation of an internal asset with a system-generated UUIDv7 `asset_id`, `name` copied provisionally from the X display name, `identity_status=pending_identity`, and `asset_kind=social_account`; it maps the observed X ID to that same asset_id in #1002, and a repeat lookup must reuse it. The social-account kind is based on the observed source, while the identity status remains pending until review clarifies what this account represents. #4002 periodically asks AI to propose names, relationships, and possible corrections. #4003 lets a person decide whether each proposal is correct. Only approved proposals proceed to #3003, which specifies the resulting change to #1001 or #1002 while preserving stable asset IDs and a separate review record. No AI review or correction has run here. Discovery alone does not establish that an account is an official project identity or that its asset has been verified.

The #5001 design contract is `catalog/score-event-topic-proposal.v1.json`. The user-provided fewunderstand registry has ten broad `<domain>.<type>` topics; none reasonably hosts an accepted, replayable scoring ledger event. In particular, `signal.data` carries strategy signals rather than accepted score contributions, and `indicator.data` carries computed indicators rather than immutable score facts. SignalStudio therefore proposes exactly one broad candidate, `score.events`, subject to fewunderstand review; it is neither an approved name nor an existing Topic. Following fewunderstand’s existing Header convention, the three proposed Headers are `source=signalstudio` (logical business origin of #3006, not a claim of a running SignalStudio process or the original crawler), `type=score_event` (accepted scoring-event family), and `category=asset_score_contribution` (specific business event). Their exact tuple maps to one proposed fewunderstand registry entry with meaning, pinned Value schema `score.asset_score_contribution.v1`, consumer routes, and destinations. Both independent consumers read the message, look up the tuple and validate Value.data before their respective idempotent write; unknown tuples must not be silently processed. Redpanda does not filter on Headers. `record_type` is represented by `category`, and the v1 schema is registry metadata rather than a fourth `schema_version` Header. An incompatible future schema requires a distinct registered discriminator agreed with fewunderstand before emission. Value.data holds the eight #1005 fields, including immutable `decay_policy_ref` and positive `half_life_minutes`; no asset, score, rule, decay, or duplicate `payload_schema` Header is needed. The current one-partition demo intentionally leaves Message Key unset; `event_key` in Value.data handles deduplication. Revisit a per-asset key only if partition count grows and per-asset ordering becomes necessary. The Redis projection and Delta/Parquet archive use separate consumer groups so each reads all events and commits its own offset only after an idempotent `event_key` write. The Topic must retain all events until archival and the agreed replay horizon are covered, without compaction by asset key; fewunderstand decides the concrete retention and implementation. No Topic, consumer, Redis projection, archive, or header registry run is claimed.

The planned first-asset score is defined in `catalog/identity-flow-case.v1.json`. Both #3002 newly created assets and #3004 already mapped assets route to #3009. Only `action=created` after successful #1001/#1002 writes makes #3009 save a durable score decision and submit one `score_key=total_heat, score_delta=+100` event to #3006, then #5001. `action=reused` emits no initial score event; a missing legacy score needs a separate backfill. `asset_initial_score/v1` is the contribution rule, not a separate ranking metric. The stable event key derives from asset ID, score key, and durable `asset_initial_score/v1/{asset_id}` decision reference; retry must reuse both. The proposed #5001 Value.data carries both immutable `decay_policy_ref=asset_initial_score/v1` and `half_life_minutes=10080`. #3006 validates that the positive number matches the referenced rule and freezes both when the event is first accepted; retries reuse them. #3007 would copy both into #6001 Redis; #3005 uses the stored number for the exponential formula and the reference for model and version validation. #3008 archives both in #1005, so replay preserves the original parameters. `decision_ref` still traces the detailed scoring decision. The 100 points are the starting contribution, not a value that remains 100 on a later lookup. These are specified outcomes, not executed score records.

The card details now carry the same selectable #2030 account case through #3009, #3006, #5001, #3007, #6001, #3005, and #1006, with a separate #3008 → #1005 archive branch. The observed Kaito MCP account ID, name, and fields anchor the case; lookup, asset creation, score decision, event key, acceptance timestamp, Redpanda message, Redis record, archive row, and calculated score remain specified outcomes until the backend runs. #5003 shows all 16 fields from the saved Kaito response as intended Topic data, while #5002 shows only the four fields saved from a real CoinGecko HTTP response; neither Topic has a verified emitted message. The #1005 and #1006 cards keep empty raw tables and show a separate planned row preview, because required runtime values cannot be truthfully populated yet. The initial-score half-life is 10,080 minutes with continuous elapsed time from event entry. The #1006 preview still shows its formula because the actual score-entry and calculation timestamps do not exist yet.

The #5002 → #3001 branch also shows the saved Bitcoin market sample. Its observed volume divided by market cap is about 0.01883, below the unvalidated 0.2 design threshold. This manual substitution is not an executed signal: the saved response omitted `id` and `last_updated`, both needed for a complete processing record, and no crawler or Redpanda message has been verified.

Graph edges only connect cards and show direction; they do not own a transport, storage, calculation, or business rule in the user-facing design. Redpanda Topics have their own `#5xxx` cards, and Redis recent windows have `#6xxx` cards. A Topic card carries its name, message key, schema, and independent consumers, so one producer can fan out to several consumers. Table cards describe storage semantics; processing cards describe reads, writes, and transformations. The browser should receive a backend response containing the related assets; it should not query these tables directly. Overview opens the single complete saved graph, including unconnected upstream operations and planned business tables. Fit the canvas to that full map on entry; users can zoom, search, and filter by path or type. The table view lists current upstream operations alongside designed nodes. Signal path and Asset knowledge path are filters over that same graph. Source details can count designed destinations and downstream nodes, but a trace for a specific crawled record requires execution lineage: a stable observation/message ID, processing run and version, Redpanda topic/offset or equivalent source position, generated result IDs, and recorded fan-out. No database queries, Redpanda consumers or record-level traces are implemented by a graph connection.

The Topic card describes message transport; the receiving program card describes parsing, processing, and the result. Keep the Topic name, message key, schema reference, known `data` fields, Headers, and consumer groups on the Topic card. Do not add a default `meta` block. Preserve the full upstream record in `data`; label fields derived from source contracts or saved upstream responses as planned until emitted Redpanda messages are verified. A Redis card describes its window, lookup keys, and rebuild path. Keep backend edge IDs and field mappings only as internal execution metadata; graph lines have no visible L label, method selector, or separate detail panel.

For a versioned signal, selecting its Redpanda Topic card should show its message envelope and key, every declared upstream field path inside the payload, Headers, and evidence status. The downstream node owns the smaller set of consumed message paths, field mappings, calculation, trigger, and output. The exported package may retain internal connection IDs to describe field lineage, but user-facing transport meaning belongs to the Topic card. Mark upstream field inventory as a contract lower bound and the message envelope as a plan until real emitted messages are reported. A graph connection cannot show a particular record's journey without execution lineage.

The Arrange nodes action keeps connected dependencies left to right. Unconnected upstream operations are packed into compact blocks by source, and unconnected business tables form their own block. The source and table headings are visual labels, not additional saved graph nodes or relationships.

The graph also offers a read-only One-step relationship view for dense flows. It shows one selected card between its direct inputs and outputs. Selecting a neighboring card moves the focus; connection lines only show direction and have no separate inspection view. A table read and later planned write may place the same table on both sides. This is a different presentation of the saved graph, not an additional node, edge, or execution trace. The full graph remains available for spatial overview and editing.

In the full graph, connections use curved routes and separate attachment points on cards; specified table writes attach below the cards. Hovering or selecting a card emphasizes its direct neighbors. Decision styling marks the #4001 lookup and other review decisions. #4001 route labels describe the branch conditions; the saved case supplies real source values and specified results for the first lookup, paired table rows, and repeated input. Curves improve readability without guaranteeing that all crossings disappear.

Every saved graph card has a four-digit reference shown on the card, table row, and detail panel: `#1xxx` for business tables, `#2xxx` for upstream operations and reference resources, `#3xxx` for processing programs and outputs, `#4xxx` for checks and decisions, including rule evaluation and branch-routing lookup, `#5xxx` for Redpanda Topic cards, and `#6xxx` for Redis window cards. An asset or relationship lookup can be classified as a program or a decision when created. Within each group, assign numbers from 1 in the order cards are created. Search accepts a full reference or a group prefix such as `#2`. The one-time migration of existing cards keeps their internal IDs, fields, connections, and internal L/R references; saved prose references are updated to the new numbers. After migration, numbers persist across renames and layout changes and are not reused after deletion.

For a source whose name alone does not explain its use, show a short purpose on the card and a concrete input → expected output → next processing step explanation in its detail panel. Label examples as illustrative and distinguish observed upstream API fields from crawler records and deployed processing. A source node is a record-type design reference, not an interactive query form.

## Crawler input and output understanding

Maintain the application-owned, versioned contract in `catalog/source-contracts.v1.json` for each desired upstream operation. Few Understand consumes it to implement crawlers and reports implementation status and real emitted records separately; it does not define desired source fields for this product. The assistant should record the user-facing purpose; required and optional inputs with meanings, accepted values and defaults; an ordinary-language example and its resolved parameters; output record types and key fields; one clearly labeled response example; provenance; and the next useful processing step. Track separately whether each item comes from an upstream API sample, crawler code or fixture, observed crawler run, or design hypothesis. Unknown parameters and unverified output mappings must stay explicitly unknown. A declared output field or test fixture is not evidence that a crawler has emitted that record in production.

When a user describes a need in natural language, the assistant identifies the subject, time range and intended question, selects a candidate operation, and shows the proposed input interpretation before any future execution. It then explains returned records as concrete business objects with source evidence and validation status. If the input contract is incomplete, it describes the intended query and missing contract instead of inventing exact API parameter names or claiming it can run. Persist accepted interpretations and contract revisions in project state so later sessions can use them.

For `kaito.mcp.kaito_events`, explain that a source event is a candidate occurrence or catalyst with references. It is different from a downstream `Signal Event`, which would be emitted only after a versioned rule evaluates evidence. The contract has a small MCP response sample, but no verified crawler run for this operation.

The current `kaito-social-spider` implementation calls `kaito_events` with `entity`, `window`, and `limit`; its configured defaults are `next_14d` for the event window and 50 for the candidate limit. The entity comes from candidate discovery or a configured watchlist. This is evidence of how crawler code forms a request, not proof that the upstream API accepted a particular call or that a production crawler message exists. Natural language is a future assistant interface that would resolve a user's project and time request into supported parameters; the upstream operation node itself is not that interface.

`kaito.mcp.kaito_search` and `kaito.mcp.kaito_advanced_search` are separate upstream operations, not search boxes in the current canvas. The current crawler automatically calls `kaito_advanced_search` for candidate entities with structured filters. Design material describes `kaito_search` as natural-language search, but the crawler does not currently call it. The assistant should name the operation that produced a result and explain its actual input contract.

Saved connections retain internal `L` identities for field lineage and migration, but those numbers are not shown on lines or used as user-facing cards. Field usages retain `R` references for technical inspection. Search by `#` card reference or name; a field usage reference can locate its connected cards. These identify saved design objects, not observed crawler records.

## Multi-agent option

When an investigation benefits from parallel perspectives, one agent can propose candidate methods, one can check them against available data, and one can challenge assumptions and likely false positives. A coordinating assistant should reconcile their findings into a short, reviewable proposal. Multiple agents are an implementation option, not a requirement for the user to operate the product.

## Where this guidance lives at runtime

This document is the product specification. `AGENTS.md` gives Codex project guidance when working in this repository. Neither file is automatically applied to an AI embedded in the web page. When that assistant is built, keep its versioned instructions in server-side application code, load the current crawler catalog and saved project decisions as request context, and persist conversation or research state across sessions. Do not depend on the user's Codex conversation as the product's memory.

The current app supports catalog browsing and drafting graph nodes and connections. Its natural-language proposal only drafts a node with dependencies. It does not yet inspect posts, orchestrate research agents, run signal calculations, or store a product-assistant conversation.

A signal execution package separates required behavior (source inputs, calculation, trigger, output and evidence) from preferred implementation technology. Mark the target platform and suggested products or components, such as Polars for a calculation in Few Understand, as design guidance with an explicit verification status. The implementing platform chooses the actual component and reports that choice and any deviations. Finding a library or processor in its repository is code evidence, not proof that this signal has run on it.
