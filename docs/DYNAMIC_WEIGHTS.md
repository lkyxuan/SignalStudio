# Dynamic weight library (SS-113)

Approved on 2026-10-18: four Studio table cards, schemas, fictional cases and
reference bindings. [Decision and approval](https://app.notion.com/p/3fd038a63d5a818c8e04d003e04b7b61).
`catalog/dynamic-weights.v1.json` owns the examples and card rules;
`catalog/business-tables.v1.json` exposes their portable logical schemas.

## Identity and scope

An account and its owning project are distinct rows in #1001, each with its own
UUIDv7 `asset_id`. #1002 maps the stable X user ID to the account. #1003 expresses
reviewed ownership; it neither merges identities nor propagates scores. An
existing account ID must be reused, never regenerated by the weight module.
The two fictional project-P accounts are also shown in the existing identity
cards, with separate forward/reverse relationship row IDs. No live account or
review is created by these examples.

Account-scoped rules reference `subject_asset_id` in `assets`, not the owning
project. A project-scoped rule, if later supported, must explicitly target the
project. Source IDs and signal types remain separate dimensions, not invented
assets. A message's target asset and topics require their own evidence; ownership
alone does not assign its contribution. A person's account weights do not
automatically inherit the person's rules or vice versa.

## Four logical tables

- `weight_topics`: stable topic IDs, names, definitions and active/retired status.
  Topic IDs do not add a new asset kind to #1001.
- `weight_rules_current`: one current rule per purpose/layer/signal/source/subject/
  topic scope. Nullable scope dimensions mean defaults only where the layer
  allows them. Explicit scope checks and a null-safe unique index distinguish
  defaults from duplicate configuration. The coefficient is finite and nonnegative.
- `weight_rule_versions`: append-only version identities, immutable scope/value,
  effective time, reason and method, plus evaluation IDs when available. Manual
  examples may have no evaluation IDs. Automatic updates must cite completed
  evaluations under a defined method; that method is not implemented here.
- `weight_evaluations`: one judgment, subject, topic, evaluation goal and observation
  window with pending/evaluated/inconclusive state and outcome evidence. Pending
  does not mean false. An evaluated result requires evidence, method and an
  evaluation time at or after the observation window ends.

The SQL is an executable SQLite reference for structural checks, not a production
migration. Current rows mirror the selected version for efficient batch loading.
Publication must validate **all** scope fields against that exact version, plus
subject-kind applicability and every evaluation reference. The reference foreign
key checks version identity, rule identity, coefficient and effective time; it does
not replace the remaining publication checks. Update current rows and historical
versions atomically; do not change old versions. No production publisher exists.

Within one layer select a unique applicable rule: an account/topic override
replaces its account default. A source-specific account rule can override a
source-independent rule only under an explicit precedence policy. Incomparable
matches must block publication rather than fan out and multiply contributions.
Missing defaults and missing required configuration need explicit handling, not
an invented successful score. The shown cross-layer multiplication and numbers
are illustrations, not an accepted scoring formula or calibrated parameters.

## Runtime requirements, not runtime evidence

Batch readers extract distinct scope keys, load a bounded working set and use
equi joins or memory lookups. Pin a complete immutable configuration snapshot per
batch; keep its revision in the durable scoring decision. Current rows alone do
not implement an atomic multi-process snapshot publication protocol. That protocol,
cache propagation limits and failure policy remain to be designed and verified.

Do not query the database once per message, enumerate every possible scope
combination or load evaluation evidence into the scoring path. Chunk large working
sets and prevent many-to-many join amplification. Statistical updates should use
newly evaluable evidence and handle window expiry according to the chosen method.
No update algorithm or scheduler is installed. Historical replay uses the version
and evidence available then; retries use the original durable decision. Existing
event decay continues to use frozen contributions, without looking up new weights.
The existing #6001 event cache is not a weight cache.

Throughput, memory, cold/warm lookups, update contention and cache freshness have
not been measured. Deployment acceptance must measure these against actual message
and distinct-key volumes; schema tests are not performance evidence.

## Studio delivery and verification

`server/dynamic_weights.py` transactionally adds four table cards and reference-only
edges, allocates #1xxx IDs and preserves existing cards, positions and user edits.
It rejects naming conflicts and rolls back interrupted installation. All bindings
have `trigger=none`, action IDs are empty and observed rows are empty. Opening a
card runs no evaluation, score update, subscription or business-table migration.

The shared BusinessTableCard/BusinessTableRows and CardDetails show bilingual rules,
fictional rows, account/project identities, version and evaluation boundaries.
Existing #1001/#1002/#1003 gain only fictional account/ownership examples; their
field contracts and #1004 remain unchanged.

Verify with `PYTHONPATH=server python3 -m unittest server.test_dynamic_weights`,
`npm run test:contracts`, `npm run test:layout`, `npm run build`, and
`npm run check:details -- <saved-graph.json>`. The Python checks exercise null-safe
uniqueness, references, version/value consistency, evaluation state, additive
installation, idempotency and transaction rollback. Graph installation creates no
physical `weight_*` business tables.
